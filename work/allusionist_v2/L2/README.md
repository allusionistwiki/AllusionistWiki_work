# L2 — 名前統合・正規化層

L1（機械抽出）の産出物から、**同一実体の名前のゆらぎを統合した正規化エンティティ台帳**を作る層。

## 入力 / 出力

- 入力: L1 run（`work/allusionist_v2/L1/runs/<id>/facts/` の人物・用語エンティティ、`_merged/` の統合履歴）
- 出力（run 産出物）:
  - `clusters.json` — 名相関グループ（エッジ型・統合裁定・確度。下記「名前統合案」）
  - `entities.json` — 正規化エンティティ台帳（台帳は単一ファイル可、run 内で完結。裁定確定後の clusters の射影）
  - `aliases/chNNNNN.json` — 話単位：L1 名義 → 正規名 対応（来歴）

## entities.json スキーマ（初 run 設計）

```json
{
  "schema": "l2-entities/1",
  "entities": [
    {
      "id": "E_<slug>",                  // 安定 ID（正規名 slug、以後不変）
      "canonical": "トリシューラ",        // 正規名
      "aliases": ["トリシーラ", "トリシュラ"],   // 統合された名義（誤記・prefix 付き含む）
      "kind": "character|term|org|item|motif",
      "first_seen": {"ch": "ch00001", "para": 12},   // L0 アンカー
      "l1_refs": ["<run_id>:facts/chNNNNN#<fact_id>", "..."],
      "merge_evidence": "明言|蓋然性高|要検証",       // 統合根拠の確度
      "notes": "prefix 修正・一人多名称の判定メモ"
    }
  ]
}
```

## 運用則

- **統合は追加専用**: 一度発行した `id` は不変。名前の再分割・再統合は新 run で行い、`aliases` の移動として記録（旧 run は書き換えない）。
- 確度ラベルなしの統合は禁止（vault の「推測はラベル付き」鉄則と同一）。
- 一人多名称（別名・あだ名・prefix 付き表記）は 1 entity + aliases。別人同名は別 id + `notes` に区別根拠。
- 来歴: `l1_refs` で L1 fact → L0（chNNNNN + ¶N）まで辿れること。
- 初 run は移行戦略（下記）に従い L1 run 和集合（baseline + 5xxx 全話）の名義棚卸し（初回のみ全量）。以後は新話着時のみ増分 run。

## L1⇒L2 移行戦略（2026-10-24 検討・数値は全て実測）

### 現状計測
- L1 稼働: baseline `20261012T0000_baseline`（ch0001〜ch0264・facts 20,070 件）+ カクヨム全話再生成 `20261021T1727_9c2e`（ch5001〜・facts 18,670 件、来歴は f863 経由で L0 ¶N に接続）。
- 名義 surface: facts subject ユニーク **14,897**（両 run 和集合、共通 3,470）。entity_type 別最多は terminology 13,484 / character 11,998 / item 7,581 / organization 2,944（件数ベース）。
- 表記正規化（NFKC+空白除去）で統合できるのは **24 件のみ** → 名義ゆらぎはエンコード問題ではなく実体同一性判定の問題。
- 既存公開エンティティ: vault `wiki/entities/` に **5,969 ページ**（E_char 3,774・E_term 1,062・E_item 620・E_org 401・E_motif 74・E_phrase 32）。= 事実上の L2 断片が先に公開されている。
- 断片実測（L2 の実作業対象）: 正規化表示名でグループ化すると 4,582 ページ（非容姿）→ 3,728 グループ、うち **610 グループが複数ページ（1,464 ページ）**。すべて同一名の kind 横断（例: ちびシューラ = char/item/org/term の 4 ページ、Spear = char/item/term）。facts subject と完全一致する既存公開名は 1,270 のみ → 残り ~13.6k 名義は台帳外の未整理 surface（多数は文・句レベルの非エンティティ）。

### 方針
1. **初 run = 和集合 861 話の全量棚卸し**（README 旧想定「初回 272 話→以後増分」を改定: 589 話が既に増殖済みのため、初回のみ和集合全量、以後増分）。`run.json.derived_from = ["20261021T1727_9c2e", "20261012T0000_baseline"]` で来歴を繋ぐ。
2. **3 段方式（LLM 負荷の封じ込め）**:
   - **Stage A（機械・LLM 無し）**: 既存公開 ID 5,969 を台帳の骨格としてシード（公開 ID・ページ・グラフリンクは不変の権威）。NFKC 正規化一致、facts subject ↔ 公開表示名の完全一致 1,270 件をシード紐付け。
   - **Stage B（機械・候補生成）**: 同一 name 複数ページ 610 グループ、正規化 edit 距離 ≤2、 substring/接頭辞（様・氏・先生・敬称）、fact 内共起ペア → 裁定候補リスト（数百〜2 千組想定。14.9k 全ペア 2.2 億は LLM に出さない）。非エンティティフィルタ（長い述語文・引用断は rejected キュー）。
   - **Stage C（LLM 裁定・Strata 直列）**: 裁定は**相関グループ単位**（下記「名前統合案」）。グループの全変種＋根拠 quote を 1 回の提示に出し、変種ごとに `alias（同一）/別 entity/要検証` + 確度を出力。判定不能は review キュー（reanchor の収束パターン踏襲）。裁定候補は 1〜2 千グループ × 1 裁定 ≈ 1〜2 時間。
3. **ID 則**: 既存公開 ID を canonical として採用・不変。統合は aliases 移動として記録（ページ削除・ID 再発行なし）。同一名の kind 横断は「同一実体・多面」が多数 → 1 entity 1 kind + `notes` に側面記述、確度ラベル付き（別人同名のみ別 id — 既存則の反転例として運用則に追記）。
4. **産出物**: `clusters.json`（名相関グループ・エッジ型・裁定状態・確度。Stage C 産出）+ `entities.json`（台帳 = 裁定確定後の clusters の射影）+ `aliases/chNNNNN.json`（話単位来歴）+ `rejected.jsonl`（非エンティティ除外台帳）+ `run.json`。`latest.txt`・`runs-index.json` L2 更新。
5. **公開連鎖**: 生成器 `build_l2_pages.py`（新規）→ vault `wiki/l2/`（index.md + 台帳一覧 1 ページ + 台帳データ。個別ページは必要時に台帳から生成）→ CI 配置 → 下層Wiki索引の L2 を「稼働中」へ。build_folder_indexes の LABELS 対象に追加必須。断片 610 グループの alias リダイレクト（L7/L1 側整理）は台帳確定後の第 2 ラウンド。
6. **検証**: l1_refs サンプリング→ facts ファイル→ ¶N 到達確認 / 名義 surface カバレッジ統計 / 610 グループ処理率 / lint（ID enum）/ 公開ページ broken 0。

## 名前統合案 — 名相関グループ（2026-10-24・ユーザー指示）

単位は「ペア裁定」でなく**相関グループ**: 特定の名義を入力すると、相関する全名義がエッジ付きで提示され、そのうち**どれを統合しどれを統合しないか**をグループ単位で裁定する。

### エッジ型（相関の分類・機械検出）
| エッジ型 | 例（実データ シナモリ/アキラ 171 名義 572 facts より） | 統合規定 |
|---|---|---|
| **表記ゆれ**（中点・全半角・空白・括弧注記） | シナモリアキラ x165 ＝ シナモリ・アキラ x37、`俺（シナモリアキラ）`、`アキラ（シナモリアキラ）`（括弧 alias 構造は主名↔括弧内を自動抽出） | 自動統合（確度: 蓋然性高） |
| **省略・敬称・あだ名**（接頭辞/接尾辞除去で一致） | アキラ x91（根拠 quote「アキラ。シナモリ、アキラ」）、アキラくん、ちびアキラ | 裁定対象（同一所指の可能性高いが個別証拠で判断） |
| **同人名**（部分一致するが別人） | ゾーイ・アキラ x15（【力士】のゾーイ・アキラだ。） | 統合禁止（別 id + 区別根拠を notes） |
| **派生・関連語**（X選・Xの右腕・紀人都市X 等） | シナモリアキラ選 x7、紀人都市シナモリアキラ x5、アキラの右腕 x5 | 統合しない。entity 間の**関係エッジ**として残す（alias にしない） |

→ 「相関する語の提示」と「統合の可否」は別物: 提示は全エッジ、統合は表記ゆれ＋裁定で同一と判定した省略形のみ。関連語は L2 台帳の関係として保持し L3/L5 で使えるようにする。

### 処理
1. **相関グラフ生成（Stage B・機械）**: 正規化キー（NFKC＋中点/空白除去→同一は表記ゆれ）＋部分一致＋敬称除去＋括弧注記解析＋fact 内共起 → 名義→相関セットの提示可能なグラフ（`clusters.json`）。
2. **自動統合ゲート**: 表記ゆれエッジのみ自動統合（確度 蓋然性高）。それ以外のエッジは必ず裁定。
3. **グループ裁定（Stage C・LLM・グループ単位）**: 1 グループの全変種＋根拠 quote を 1 回の提示に出し、変種ごとに `alias（同一）/別 entity/要検証` + 確度を出力。**ペア裁定にしない理由**: A=B, B=C, A≠C の移行的矛盾（シナモリアキラ＝シナモリ・アキラ＋アキラ 鎖、ゾーイ・アキラで切る）をグループ同時裁定のみ回避できる。
4. **台帳は裁定の射影**: `entities.json` は裁定確定後の clusters から生成。旧 run の cluster 構造は不変、移動は新 run の差分として記録（追加専用則と同一）。
5. **提示面（公開）**: 相関索引ページ（`/AllusionistWiki2/l2/`）で「シナモリアキラ → シナモリ・アキラ(表記ゆれ・統合済) / アキラ(省略・裁定済同一) / ゾーイ・アキラ(同人名・別 entity) / シナモリアキラ選(関連語・非統合)」のように**エッジ型・統合状態・kind・確度**を表示。参照 API は `clusters.json` を機械読取で提供する（L3 以降の生成器もこれを使う）。

### kind 決定（名義→character/item/… の属性・2026-10-24 実測）

入れた名前が character か item かなどの属性は、**facts の entity_type 票 + 既存公開ページ prefix を材料に、機械投票→少数の裁定**で決める。

- 実測: 14,897 名義のうち **90%（13,432）は単一 kind のみ**、明確多数派（3 倍差・5 票以上）が +208。裁定が要るのは contested 687 + 完全同数 570 ≈ **1,257 名義のみ**（LLM 負荷は小さい）。
- 規定: ① 単一 kind → 機械採用（確度 蓋然性高）。② 明確多数派 → 機械採用（票割合を `kind_votes` に保持）。③ contested/同数 → グループ裁定（Stage C）で canonical kind を判定 — 根拠 quote に「その名が何として振る舞っているか」が写るため裁定可能。
- 多面の扱い: シナモリアキラ（character 100/terminology 44/organization 12）のように票が割れる名義は「人物その物 vs 派生した組織・流派・語としての用法」の区別 → **本体 entity は 1 kind、派生用法は別 entity（関連エッジで結ぶ）か notes の側面記述**を裁定で決める。ちびシューラ（char 112/item 34）型がこれ。
- 公開ページ prefix（E_char_ 等）は prior 票として投票に合流させる（公開 ID の kind は不変の canonical、裁定で矛盾が出たら notes に記録しページ側は第 2 ラウンドで alias リダイレクトと併せ整理）。
- 提示面では全名義に kind を付す: 確定（機械）/ 裁定済（+確度）/ 裁定中 / 非エンティティ（rejected）。
