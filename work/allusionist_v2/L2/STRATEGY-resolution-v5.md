# L2 名前統合 strategy v5 — 1 episode ずつの実読に基づく逐次解消

## 問題
v2〜v4 までの統合は「名前の統計（頻出・共起・部分文字列）」を主体に裁定した。
統計は文脈を知らないため、

- 別实体の同名・近似名（自己愛 / 紫 型）の区別
- 代表名（primary）の選定（アズ vs アズーリア・ヘレクレジュ）
- 章をまたぐ別名・変名・転生名の来歴追跡

で精度が出ない。機械監査（v4）は過剰統合の「疑い」までしか言えない。

## 基本方針
**各エピソード（章）を実際に読んで、その章の文脈の中で名前同一性を裁定する。**
統合せずにはおけない明示（自己紹介・呼称・「XはYである」・通称宣言）を
一次証拠とし、統計は補助（候補列挙・矛盾検出）に限定する。

## 手順（章逐次）

1. **章順の逐次読み**（第1話→最終話）。台帳状態は読み進みに応じて成長する
   （後章で導入される変名・転生名を、導入章の文脈で既存实体へ連結）。
2. 章ごとに LLM へ渡すものは:
   - 章全文（原文。行番号付き = ¶ 引用用）
   - **その章に出現する名前の台帳抜粋のみ**（Aho-Corasick で抽出した
     present names の实体行: canonical / kind / 既知 alias）。全 1.7 万件を
     文脈に入れない — 章文脈に無関係な台帳はノイズ。
3. LLM 出力（章ごとの証拠レコード、追加専用 JSONL）:
   - `mentions`: 名義ごとの章内役割（誰が何をした中の name か）
   - `identity`: 同一性判定 `{a, b, kind: explicit|strong| weak, quotes:[¶]}`
     - explicit = 本文に同一性述語（名乗り・呼称・「XはY」・通称宣言）
     - strong  = 同一 scene の連続動作・排他的役割同一（一人二役記述）
   - `separations`: 同一 scene で両名義が**独立の行為主体**として動く証拠
     （= 統合矛盾の反証）
4. **決定論的アグリゲータ**（LLM 使用なし）が台帳 v5 を生成する:
   - 統合適用 = explicit 証拠 1 件以上 かつ separations 反証なし
     （章号・行引用つき）。strong のみ = 要検証（本文置換しない）。
   - 降格 = 明示統合先への separations 証拠（独立行為主体）→ 要検証。
   - primary（代表名）= 名乗り・正式呼称が明示された章の名前。
     略称・呼び捨ては alias。フル表記（姓付き）の宣言があればそちらを primary。
   - 全 pair の決定には**使用章全数の読み**を要求（恒久基準）:
     統合される名義の使用章集合 ⊆ 読了章集合 で初めて適用。
5. 来歴: 章ごと証拠レコード（`episodes/<ch>.json`）と決定ログを run として
   追加専用保存（derived_from: v4）。旧 run は不変。

## 実装
- 生成器: `scripts/l2_name_resolution.py`（章逐次 LLM 読了 → 証拠レコード）
  - Strata API（llm_client 共通・プロセス内スロットル）
  - 進捗: `episodes/` に章ファイル（既存の再解析進捗様式）
- 集計: `scripts/l2_resolution_aggregate.py`（証拠 → 裁定 → 台帳 v5・審査レポート）
- 検証: 台帳 v5 で正規化 wiki 再生成 → 代表例（アズ / 紫 / 自己愛 / シナモリアキラ）の手点検

## 運用
- 章順厳守（逐次の来歴が統合の根拠）。章内並列は章単位でのみ安全。
- 1 章 1 レコード。再実行は同一章の上書き（同一章の再読のみ許可）。
- LLM 出力は JSON schema 検証。失敗章は needs-reanalysis 相当で再読。
